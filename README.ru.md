# EnvLatch

**Находите пропущенные переменные окружения до запуска приложения.**

[![Tests](https://github.com/sinzbtw/envlatch/actions/workflows/ci.yml/badge.svg)](https://github.com/sinzbtw/envlatch/actions/workflows/ci.yml)
[![Python 3.10+](https://img.shields.io/badge/python-3.10%2B-blue.svg)](https://www.python.org/)
[![License: MIT](https://img.shields.io/badge/license-MIT-green.svg)](LICENSE)

EnvLatch — небольшой консольный инструмент на Python без внешних зависимостей. Он проверяет один или несколько локальных файлов `.env` по списку ключей из хранящегося в репозитории `.env.example`. Используйте его при настройке рабочего окружения, перед запуском сервиса или при проверке конфигурации перед развёртыванием.

## Что проверяет инструмент

- По умолчанию каждый ключ из шаблона обязателен и должен иметь непустое значение; `--optional KEY` разрешает выбранным ключам отсутствовать или быть пустыми.
- Лишние ключи вызывают предупреждения; флаг `--strict` превращает их в ошибки.
- Повторяющиеся ключи и некорректные строки вызывают ошибки с номерами строк.
- Отчёты содержат имена переменных и их расположение, но никогда не содержат значения или исходные строки.
- Результаты воспроизводимы, а коды завершения подходят для скриптов и CI.

EnvLatch только читает файлы. Он не загружает переменные в процесс, не выполняет команды оболочки, не подставляет значения ссылок и не читает значения из окружения текущего процесса. Инструмент проверяет наличие и непустое значение переменных; он не проверяет действительность учётных данных, формат URL или типы, специфичные для приложения.

## Требования

- Python **3.10 или новее**.
- Windows, Linux или macOS.
- Входные файлы в UTF-8; поддерживаются UTF-8 BOM и окончания строк CRLF.

Внешние зависимости для работы не нужны. При установке pip и setuptools используются как инструменты сборки.

## Установка из исходного кода

~~~sh
git clone https://github.com/sinzbtw/envlatch.git
cd envlatch
python -m venv .venv
~~~

Активируйте виртуальное окружение:

~~~powershell
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
~~~

~~~sh
# Linux / macOS
source .venv/bin/activate
~~~

Затем установите проект из локальной копии репозитория:

~~~sh
python -m pip install .
envlatch --version
~~~

Если в вашей системе команда Python называется `python3`, используйте её при создании виртуального окружения. EnvLatch устанавливается из этого репозитория; публикация пакета в PyPI для этих инструкций не требуется.

## Быстрый старт

В репозитории есть файл `.env.example`:

~~~dotenv
DATABASE_URL=postgresql://localhost/app
API_TOKEN=replace-me
PORT=8000
~~~

Создайте локальную конфигурацию и при необходимости замените значения из примера:

~~~powershell
# Windows PowerShell
Copy-Item .env.example .env
~~~

~~~sh
# Linux / macOS
cp .env.example .env
~~~

Выполните проверку:

~~~sh
envlatch --template .env.example --env .env
~~~

Также можно запустить инструмент как модуль:

~~~sh
python -m envlatch --template .env.example --env .env
~~~

Путь к шаблону и хотя бы один путь к файлу окружения обязательны. Значения в шаблоне приведены для примера и **не** используются как значения по умолчанию: даже ключ с пустым значением в шаблоне требует непустого значения в `.env`, если он явно не отмечен как необязательный. Значение `replace-me` проходит проверку наличия; заменить заглушки на рабочую конфигурацию нужно самостоятельно.

Добавляйте в репозиторий `.env.example`, а реальные файлы окружения храните локально. Включённый `.gitignore` исключает `.env` и локальные варианты файлов окружения.

## Примеры

Потребовать точного совпадения набора ключей — удобно для автоматических проверок:

~~~sh
envlatch --template .env.example --env .env --strict
~~~

Проверить файлы из другой папки:

~~~sh
envlatch --template config/service.env.example --env config/service.env
~~~

Если в `.env` отсутствует `API_TOKEN`, значение `DATABASE_URL` пустое и добавлен ключ `DEBUG`, EnvLatch сообщит о двух ошибках и одном предупреждении. Код завершения — `1`. С флагом `--strict` лишний ключ `DEBUG` станет третьей ошибкой. Отчёты указывают имена ключей, не выводя их значения.

Посмотреть все параметры командной строки:

~~~sh
envlatch --help
~~~

| Код завершения | Значение |
| --- | --- |
| `0` | Ошибок нет; возможны предупреждения. |
| `1` | Ошибки проверки или некорректный синтаксис dotenv. |
| `2` | Неверные аргументы или имена необязательных ключей, недоступные файлы или входные данные не в UTF-8. |

## Необязательные ключи

Некоторые настройки включают интеграции, которые намеренно не используются при локальной разработке. Повторяйте `--optional KEY`, чтобы разрешить указанному в шаблоне ключу отсутствовать или быть пустым, сохранив остальные ключи обязательными:

~~~sh
envlatch --template examples/optional/.env.example --env .env --optional SENTRY_DSN --optional LOG_LEVEL --strict
~~~

В [примере необязательных ключей](examples/optional/.env.example) объявлены обычные `DATABASE_URL`, `API_TOKEN` и `PORT`, а также `SENTRY_DSN` и `LOG_LEVEL`. Эта готовая команда проверяет пример без создания локальной конфигурации:

~~~sh
envlatch --template examples/optional/.env.example --env .env.example --optional SENTRY_DSN --optional LOG_LEVEL --strict --format json
~~~

- Имя необязательного ключа должно присутствовать в шаблоне с учётом регистра. Опечатка вызывает `unknown_optional_key` и код завершения `1`, даже если такой ключ есть в файле окружения.
- Некорректные имена необязательных ключей вызывают код `2`; используется тот же ASCII-формат имён, что и в dotenv.
- Необязательные ключи могут отсутствовать, быть пустыми или непустыми. Проверки синтаксиса и дубликатов сохраняются.
- `--strict` по-прежнему запрещает ключи вне шаблона. Необязательные ключи остаются объявленными настройками, а не списком разрешённых лишних ключей.
- Правило применяется к итоговой объединённой конфигурации, поэтому пустое переопределение допустимо для необязательного ключа.
- Поле `checked_keys` в JSON и текстовая сводка учитывают только обязательные ключи. Версия схемы JSON остаётся `1`.

Без `--optional` все ключи шаблона остаются обязательными. Из Python можно передать `optional_keys=["SENTRY_DSN", "LOG_LEVEL"]` в `check()`.

## Несколько файлов окружения

Повторите `--env`, чтобы проверить общую базовую конфигурацию вместе с локальными настройками или настройками развёртывания:

~~~sh
envlatch --template .env.example --env .env --env .env.local --strict
~~~

Файлы применяются в порядке аргументов: более поздний файл переопределяет тот же ключ из более раннего. Обязательные ключи можно распределить между файлами; EnvLatch проверяет итоговую объединённую конфигурацию. Пустое значение в более позднем файле заменяет непустое значение из более раннего и вызывает ошибку, если ключ обязателен.

Например, если `.env` определяет `DATABASE_URL` и `API_TOKEN`, а `.env.local` определяет `PORT`, объединённая конфигурация соответствует шаблону с тремя ключами. Если в `.env.local` также есть строка `API_TOKEN=`, инструмент сообщит о пустом значении обязательного токена.

Повторяющиеся ключи внутри одного файла и ошибки синтаксиса в любом входном файле остаются ошибками, даже если более поздний файл переопределяет соответствующий ключ. Сообщения об итоговых ключах указывают на определение, которое вступило в силу; сообщения об отсутствующих ключах ссылаются на последний файл окружения. JSON-отчёты перечисляют `environments` строго в порядке входных файлов, в том числе при ошибках чтения.

Команды с одним файлом, приведённые выше, продолжают работать. Объединение используется только для проверки; EnvLatch не изменяет окружение процесса.

## Отчёты в JSON

Получить машиночитаемый отчёт для скриптов или CI:

~~~sh
envlatch --template .env.example --env .env --format json
~~~

Успешная проверка примера с тремя ключами возвращает такую структуру JSON:

~~~json
{
  "schema_version": 1,
  "status": "pass",
  "template": ".env.example",
  "environments": [".env"],
  "checked_keys": 3,
  "errors": 0,
  "warnings": 0,
  "issues": []
}
~~~

JSON формируется воспроизводимо и записывается в стандартный вывод как при завершённой проверке, так и при ошибках чтения файлов или некорректных именах необязательных ключей. Поле `status` принимает значения `pass`, `fail` или `input_error`. Каждая проблема содержит поля `severity`, `code`, `path`, `message`, `line` и `key`; `line` и `key` могут быть `null`, если соответствующие данные недоступны. Значения переменных окружения в отчёты не попадают.

Коды завершения остаются прежними: `0`, `1` и `2`, как указано выше. Неверные аргументы командной строки по-прежнему вызывают обычное текстовое сообщение об использовании в стандартном потоке ошибок, даже если указан `--format json`.

## Поддерживаемый синтаксис dotenv

EnvLatch намеренно поддерживает ограниченный формат dotenv с однострочными значениями:

~~~dotenv
# A comment
APP_NAME = envlatch
export PORT=8000
EMPTY=
MESSAGE="A value containing # a hash"
LABEL='A literal value'
HOST=localhost # An inline comment
FRAGMENT=https://example.invalid/#section
REFERENCE=$OTHER_VARIABLE
~~~

- Ключи соответствуют шаблону `[A-Za-z_][A-Za-z0-9_]*`; регистр учитывается.
- Допускаются пробелы вокруг ключа, `=` и значения без кавычек.
- Поддерживаются пустые строки, комментарии и необязательный префикс `export`.
- В значении без кавычек символ `#` начинает комментарий в начале значения или после пробельного символа. В остальных случаях он является частью значения.
- Значения в одинарных и двойных кавычках могут содержать `#`. В двойных кавычках поддерживается экранирование двойной кавычки.
- После закрывающей кавычки допускаются только пробельные символы и комментарий.
- Ссылки с символом доллара считаются обычным текстом: подстановка значений и выполнение команд отсутствуют.
- Многострочные значения в кавычках, символы NUL, некорректные ключи, отсутствие `=` и повторяющиеся ключи считаются ошибками.
- Обязательные ключи с пустыми значениями или значениями только из пробельных символов в файле окружения не проходят проверку.

Разбор каждого файла останавливается при первой некорректной записи, чтобы фрагмент неподдерживаемого многострочного значения не попал в отчёт как имя ключа. Дубликаты регистрируются отдельно; последующие файлы всё равно проверяются.

Шаблон и все файлы окружения проверяются одним и тем же парсером. Используйте отдельный шаблон dotenv, а не скрипт оболочки.

## Разработка

Установите проект в редактируемом режиме в своём виртуальном окружении:

~~~sh
python -m pip install -e .
python -m unittest discover -s tests -v
~~~

Пакет находится в `src/envlatch/`, тесты — в `tests/`. Для работы используется только стандартная библиотека Python. GitHub Actions запускает тесты в Linux с Python 3.10 и 3.13 и в Windows с Python 3.13.

При сообщении об ошибке приложите команду, версию Python и минимальный пример с вымышленными значениями. При изменении поведения обновляйте обе языковые версии README.
